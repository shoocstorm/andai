Architecture · Agent loop

How Andai’s agent decides, looks up and answers

Every question runs through a short loop on your computer. A decision model picks the next step, the chat model writes the tool’s arguments and, at the end, the answer, and the app’s native side checks and runs each read-only tool. This page shows how the pieces fit, step by step, with real traces from our tests.

Who does what

Four parts, one loop.

Small local models can’t be trusted to write tool calls on their own, so the work is split: the decision model only ever chooses, the chat model only ever writes (arguments held to a grammar, then the answer), and the agent code in between enforces the rules.

Agent

The loop

TypeScript in the app (agent/loop.ts, agent/turn.ts).

  • Builds the state each decision sees
  • Offers only the tools that make sense
  • Applies policies, limits and fallbacks
  • Records every step for the Execution Trace
Decision model

Picks the next step

Qwen3 (natively on MLX on Apple Silicon, else through wllama), or a Laya encoder on the Mac’s GPU.

  • Scores lettered options in one pass
  • Laya: “do the results suffice?” (yes/no)
  • Laya: how likely each passage helps, as it arrives
  • Never writes free text
Chat model

Writes

Qwen3 (0.6B or 1.7B): natively on the GPU with MLX on Apple Silicon, through wllama on WebGPU elsewhere.

  • Tool arguments, held to a grammar made from the tool’s schema
  • The final answer, citing passages as [n]
Native side + ug

Checks and runs tools

Rust, the trust boundary (src-tauri/src/tools.rs).

  • Re-validates every argument
  • Runs ug read-only, on the selected knowledge base only
  • 20 s time limit, 256 KB output cap

Inside a decision

The decision model never names a tool. It picks a letter.

Each decision gets the same three things: the state (your request, recent conversation, the knowledge base and the tool results so far), a question, and the options still worth offering. What comes back is a probability per option, so the choice is always valid and you can see how sure the model was.

Step by step

What happens at each stage, and why.

Search first, when the question plainly asks about content Agent

On step 1, with a knowledge base selected, a decision picked “search” for almost every lookup question in our tests, so a request that clearly asks about content (not small talk, has content words, not addressed to the assistant) goes straight to a knowledge search. Everything else, like “thanks!” or “who are you?”, goes to the decision model. The trace says which happened.

Decide the next step Decision model

The agent offers only what makes sense now: Answer now, the tools for this knowledge base (code tools only for code or mixed ones), and Ask to clarify. A tool that already returned something isn’t offered again; one that failed or found nothing gets one more try. Options are shuffled per turn (with a recorded seed), because option order sways small models.

  • With Laya, once there are results, “answer” leaves the choice and a yes/no question asks whether the results already suffice. At 50% or more, the agent answers, unless no passage found so far scored at least 50% on its own (below): then it keeps looking.
  • Not trusted? If the decision fails, picks something not offered, or a tool scores below 30%, the agent does what the fixed pipeline does: search once if nothing was looked up yet, else answer.
  • Not possible yet? A symbol tool before any symbol was seen looks symbols up first; Read lines before any passage searches first.

Write the tool’s arguments Chat model

Arguments are the only free text the loop asks for. The chat model writes JSON held to a grammar built from the tool’s schema, and a file, symbol or line range can only be one the results have already shown. It also sees the two most useful passages found so far, fenced as data, so a follow-up search or a line range is written from what was found. The app validates the result; if it’s still invalid, the agent searches with your question as written.

Check the tool’s policy Agent

Each tool is Auto, Ask or Off (Tools screen). The eight knowledge-base tools only read, so they default to Auto; under Ask, an approval card waits in the chat until you approve or deny.

Run it Native side + ug

The call crosses to the native side, which accepts only a closed set of tools, re-validates every argument (nothing that looks like a flag, nothing outside the selected knowledge base), builds the ug command itself, and runs it with a clean environment, a 20-second limit and a 256 KB output cap. The exact command appears in the trace.

Observe Agent

The result is summarised into the state (“4 passages: … @ file:lines”) and its passages are kept as evidence. The loop stops after 20 tool calls, after repeated errors, or when the same calls keep repeating.

With Laya, every new passage is also scored on its own, together with your question: Laya reads at most 512 or 1,024 tokens, far less than a search returns, so it never decides from the results’ text (tried: with the best passages’ text in its state it stopped sooner and found fewer facts). A long passage is scored in overlapping pieces, by its best one, and the summary line names the most useful passage and how likely it helps. The state itself is fitted to Laya’s input, so nothing gets cut off its end.

Before answering from a clipped passage (a search shows each one only up to its share of the result size, so a long section’s end can be missing), the agent reads that whole section first, with any decision model. On our eval’s long-document questions that took answers with the expected facts from 4 to 9 of 11 with Laya English, 7 to 8 with Laya Multilingual and 3 to 6 with Qwen deciding.

Before answering a question that names a symbol on a code or mixed knowledge base (cancelBooking), the agent reads that symbol’s source if the results don’t show it whole, or finds its callers when the question asks who calls it. A search often returns the passages around a named function, not the function itself.

Check relevance Decision model · Laya

Before the passages go into the answer prompt, Laya’s scores from the loop are used again (a passage that turned up without one is scored now). The top two search results are always kept; the rest are dropped below 10%; a failed check keeps everything. Sources are numbered after this, so every [n] in the answer matches the n-th source you see.

Answer Chat model

The prompt holds your persona, the passages (each fenced as untrusted data, so a document can’t give instructions), and recent conversation. The chat model streams the answer and cites passages as [n]; if nothing relevant was found, the prompt says so.

Where the decision model is used

Three jobs, depending on the model.

JobWhat it decidesQwen decidingLaya deciding
Next stepWhich tool to run, or answer, or ask to clarify, at every step (except a step-1 search first)YesYes
Stop checkWhether the tool results so far already answer the request (a yes/no question, in the same pass as the next step)No: “answer” is one of the optionsYes
Relevance checkWhich retrieved passages go into the answer promptNo: too slow per passageYes
Claim checkAfter the answer, whether each cited sentence is supported by the passage it cites; possibly unsupported ones are noted under the answer, which is never changedNo: too slow per sentenceYes
Search scopeWhether a knowledge search is focused (a name or exact term) or broad (a topic), asked in the same pass as the next stepNo: the chat model writes it with the queryYes
What it never does: write tool arguments or the answer. Those are always the chat model’s, held to a grammar and fenced prompts respectively.

The relevance check made the answer prompt 23% shorter with Laya English (the first word came about 0.6 s sooner) and 8% shorter with Laya Multilingual, with no loss of answer facts, at 36–57 ms per question.
Why not always Laya? It’s the fastest decider, but it misses small talk and its answers held the expected fact slightly less often. Qwen3 0.6B remains the most accurate choice; Laya is an option on Apple Silicon.
Guard rails

Built so a small model can’t go far wrong.

RiskWhat stops it
The model invents a tool or a malformed callIt only ever picks a letter from the options offered; arguments are held to a grammar and validated twice (app, then native side).
A guessed file, symbol or line numberThose arguments can only be values the results have already shown.
A low-confidence or failed decisionThe agent falls back to what the simple pipeline does: one search, then answer.
Endless loopingAt most 20 tool calls per question; a tool that found something isn’t offered again; repeated errors or repeated calls end the loop.
A document that tries to give instructionsPassages are fenced as untrusted data in the prompt; answers load no images and open no links; the app can’t reach the network.
A tool reaching beyond your knowledge baseEvery tool is read-only, runs on the selected knowledge base only, with a clean environment, a time limit and an output cap.
Not knowing why it did somethingEvery decision, score, tool call and relevance check is in the Execution Trace; Why this step? explains each decision.
